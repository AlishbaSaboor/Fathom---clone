3. **Today the browser uploads straight to Gemini, and Blob adds a second destination.** There are two ways to handle that:

Uploads are half the bytes from the browser, and retries are robust because Blob is durable while Gemini files expire after 48 hours. It also lets me delete the CORS workaround (`find` route, token in display name) because the server can read Gemini's reply directly. The cost is that the upload leg to Gemini changes. `analyze.ts`, the prompt, the schema, `normalize.ts` and the 30-minute cap are untouched.

   I'll go with A unless you object.

## MongoDB schema (database `fathom`)

| Collection | One document per | Key fields |
|---|---|---|
| `meetings` | meeting | `_id` (string id), `ownerId`, `shareToken` (22-char base64url, unique), `status` (`uploading` / `ready`), `title`, `date`, `durationSec`, `attendees[]` (embedded), `summaries.general[]` (embedded), `media {url, pathname, mimeType, playbackMime, fileName, sizeBytes}`, `notice?`, `model`, `createdAt` |
| `transcripts` | meeting | `meetingId` (unique), `segments[] {id, speakerId, start, text}` |
| `actionItems` | action item | `meetingId`, `ownerId`, `text`, `assigneeId`, `timestamp`, `done` |

- **Why this split:** The list page and Ask-all need meetings and action items but not the roughly 50 KB transcripts, so transcripts get their own collection. Action items are separate so the `done` checkbox can persist (today it resets on reload, which is fake state) and cross-call queries stay cheap. Attendees and summaries are embedded because they're small, they belong to one meeting, and Gemini speakers aren't people who recur across meetings. If you want literal one-collection-per-noun for 8x, I can split them further.
- **Indexes:** `meetings {ownerId, date:-1}`, `meetings {shareToken}` unique, `meetings {status, createdAt}`, `transcripts {meetingId}` unique, `actionItems {meetingId}`, `actionItems {ownerId, done}`.
- **Write order:** The `meetings` doc is created as `uploading` when the Blob token is issued. That records the pending file for quota and cleanup. The transcript and action items are written first, then the meeting flips to `ready`, so a half-written meeting never shows up. Stale `uploading` docs older than 24 hours are swept, along with their blobs.
- **Connection:** One cached `MongoClient` per instance, using `attachDatabasePool` from `@vercel/functions` as Vercel recommends.

## Blob integration and the new upload flow

I'll use a public Blob store with `addRandomSuffix`, plus `@vercel/blob/client` `upload()` with multipart for big files.

1. The browser measures duration as it does now, then calls `upload()` against `POST /api/blob/upload`. That route checks the owner cookie, enforces the pathname prefix `recordings/<ownerId>/`, a 200 MB max, the allowed content types and the storage guard, then creates the `uploading` doc.
2. `POST /api/recordings/import {blobUrl}` verifies the blob with `head()` and checks it belongs to this owner and store. It then streams the file to Gemini and returns the Gemini file name.
3. Polling `/api/recordings/file` is unchanged.
4. `POST /api/recordings/process` runs the same Gemini analysis, then builds the meeting on the server, writes it to Mongo and returns `{meetingId, shareToken}`. The browser then navigates to the meeting.
5. Sharing: `/share/[token]` reads Mongo and renders the full result with a real `<video>` or `<audio>` on the Blob URL, so seeking works. The old "recording not available in this preview" state is gone.

Some details to be aware of:
- **Public store trade-off:** A public Blob URL works for anyone who has it, but it's unguessable and only ever sent to the owner and to share-page viewers, which is the same trust boundary as the share token. A private store would need a proxy function streaming every video, which costs transfer and function time.
- **Local dev:** `onUploadCompleted` can't reach localhost, so I don't depend on it. The client-triggered import and process calls do the writes, and the server re-verifies the blob rather than trusting the client.
- **MIME types:** The Blob object gets a browser-standard type (mp3 as `audio/mpeg`, mov as `video/quicktime`). Gemini keeps its own type mapping.
- **Delete:** This becomes real. It removes the Mongo docs and the blob, and the share link dies immediately. The old "link keeps working 30 days" copy goes.
